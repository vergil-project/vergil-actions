
# Release 2.1.29 (2026-08-24)

## Bug fixes

- **wire a C++ semgrep ruleset that exists (#851) (#852)**
p/cpp is not a Semgrep registry ruleset - it 404s, so the semgrep gate failed with exit 7 on every cpp repo. p/c-plus-plus and p/cplusplus 404 as well.

p/c alone is not a fix. extra-config is the entire C++ ruleset here, because vrg-semgrep-scan's _LANGUAGE_RULESETS has no cpp key, and p/c applies rules to .c only - it scans no C++ whatsoever. Dropping to p/c would have turned a hard failure into silent zero coverage.

Measured with an identical probe.c/probe.cpp pair on semgrep 1.173.0, reading paths.scanned: p/c scans only the .c file, while p/security-audit, p/default and p/cwe-top-25 all apply rules to the .cpp file. p/security-audit also fired a real finding on the C probe (insecure-use-string-copy-fn, CWE-676). Full table in the issue.

Surfaced by logical-minds-foundry/mq-protocol-gateway, the fleet's first cpp repo.

- **state plainly that semgrep gives no C++ coverage (#853) (#854)**
Follow-up to #851/#852, which stopped the p/cpp 404 but documented p/security-audit as restoring C++ rule applicability. That claim is false and the config did not do it.

No community Semgrep pack declares a single cpp rule - measured p/c 0, p/security-audit 0, p/default 0, p/cwe-top-25 0. https://semgrep.dev/c/r/cpp returns 200 with a body of 'rules: []': the C++ namespace exists and is empty, which is also why p/cpp was never published.

The earlier conclusion came from reading semgrep's paths.scanned, where p/security-audit appeared to scan a .cpp probe. That was its 14 generic/regex rules matching any file, not C++ analysis. Direct check with gets(buf) duplicated across t.c/t.cpp/t.cc/t.hpp under --config p/c: 'Scanning 4 files tracked by git with 2 Code rules: Scanning 1 file with 2 c rules', one finding, on t.c only.

Semgrep's GA C/C++ support is Semgrep Code - Pro engine and Pro rules behind SEMGREP_APP_TOKEN - not the unauthenticated community registry this pipeline scans.
