
# Release 2.1.14 (2026-07-13)

## Documentation

- **codify the all-hard-gates principle (#765)**
* docs(ci): codify the all-hard-gates principle

Add a foundational-principles doc to the CI Gate Requirements section stating that every check that matters is a hard, asserting gate — there are no report-only or warning gates, because an unheeded warning is meaningless (reviewers optimize for can-I-merge and never revisit warnings). Deprecation warnings are treated as errors (early signal of a future outage), and the sprawling warning-exception list is rejected: if it matters, assert it and fail on it.

Cross-references the CI-evidence publish-safety property (epic vergil-project/.github#140 spec §9.1), which depends on this principle. Wired into the mkdocs nav and the ci-gates section index.

Ref vergil-project/vergil-actions#763

* docs(ci): distinguish gate deployment lifecycle from soft gates

Add a gate-deployment-lifecycle section to the all-hard-gates doc reconciling the all-hard-gates principle with staged rollout. All gates are hard as a permanent configuration — a permanent soft gate does not exist — but deploying a new hard gate is a lifecycle: it first runs in warning mode (reports, does not fail) for a bounded bake-in period to collect reliability data, then is promoted to enforcing (fatal) once proven stable.

Warning mode is a transient deployment state of a hard gate, never a permanent soft gate; the end state of every gate is always enforcing. Uses the CI-evidence gate (epic vergil-project/.github#140) as the concrete example: warning mode first, bake across release cadence, single flag flip to enforcing. This refines rather than contradicts the existing content — the unheeded-warning anti-pattern is the permanent report-only case, not the time-boxed, owned, promotion-committed deployment stage.

## Features

- **emit ci-evidence-<gate> artifacts from gate workflows (#764)**
Add a shared actions/ci/evidence/emit composite that writes an evidence.json fragment ({gate, tools, metrics, files}) and uploads it, together with any available report files, as a ci-evidence-<gate> workflow-run artifact for the release-time harvester (vrg-ci-evidence).

Wire it into all four required gate workflows via a dedicated needs-gated evidence job so the artifact's presence is itself proof the gate passed, and so each gate emits exactly one artifact despite its matrix/multi-job structure (upload-artifact forbids same-name uploads across jobs):

- ci-test, ci-audit, ci-quality: one evidence job that runs after the gate's check jobs succeed.
- ci-security: each scanner (codeql, trivy, semgrep) uploads its SARIF as an evidence partial UNCONDITIONALLY (independent of the code-scanning upload), and a consolidation job merges the partials into the single ci-evidence-security artifact. This lets the harvester read artifacts only, with no code-scanning API dependency (spec section 7).

Report-file globs (coverage.xml, junit.xml, pip-audit.json, licenses.json) are forward-compatible: they are skipped until the check commands emit them, so test/audit/quality currently produce an evidence.json-only artifact, which is sufficient for completeness.
