# vergil-actions v2.0 → v2.1 Canary Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Move vergil-actions onto the v2.1 tooling line and prove, via its self-referential CI, that v2.1 validates cleanly — the lowest-risk canary for the fleet-wide 2.0 → 2.1 migration.

**Architecture:** Three source changes plus a docs sweep, all on `feature/679-vergil-2.1-canary`. The functional core is the `vergil.toml` pin (Axis 1 — drives which `vergil-tooling` tag installs) and one GitHub Actions git ref (Axis 2 — `standards-compliance` → `@develop`). The rest is a consumer-facing doc sweep of stale `@v2.0` references. There is **no** `VERSION` bump: `develop` (2.1.1) already diverges from `main` (2.1.0), so the version-divergence gate passes as-is. Verification is two-gate: local `vrg-validate` + PR CI now (CI gate); the first post-merge release later (CD gate).

**Tech Stack:** GitHub Actions composite actions + reusable workflows (YAML), `vergil.toml` repo profile, `vergil-tooling` CLI (`vrg-*`), container-based validation (`vrg-container-run -- vrg-validate`), MkDocs docs site.

**Spec:** `docs/specs/2026-06-04-vergil-2.1-canary-design.md`
**Issue:** vergil-project/vergil-actions#679 · **Playbook:** vergil-project/vergil-tooling#1371

> **Note on TDD:** This is a configuration/documentation change with no unit-testable code. The analogous discipline is **validate after each change**: make the edit, run the relevant check, confirm it passes, commit. The authoritative check is `vrg-container-run -- vrg-validate` (the only validation command for this repo); CI is the acceptance gate.

> **Working location:** All edits and git operations happen inside the worktree `/.worktrees/issue-679-vergil-2.1-canary` on branch `feature/679-vergil-2.1-canary`. Use absolute paths or `cd` into the worktree first. Use `vrg-git` / `vrg-commit` / `vrg-gh` (raw `git`/`gh` are denied).

## Task 2: Track @develop for the standards-compliance setup ref (Axis 2)

**Files:**
- Modify: `actions/ci/security/standards-compliance/action.yml:13`

**Why:** This is the one absolute remote `uses:` ref in executed code (it must be absolute because the action is consumed remotely by other repos, where a `./actions/...` relative path cannot resolve). On `develop` it should track `@develop` so the self-referential PR exercises the current line; `freeze-internal-refs` pins it to `@v2.1` at release. The `@v2.0` value was a stale bootstrap leftover. **Do not change this one to `@v2.1`.**

to:

- [ ] **Step 3: Commit**
