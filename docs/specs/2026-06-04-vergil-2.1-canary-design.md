# vergil-actions v2.0 → v2.1 canary — design

- **Issue:** vergil-project/vergil-actions#679
- **Playbook (fleet docs):** vergil-project/vergil-tooling#1371
- **Date:** 2026-06-04
- **Status:** approved (design)

## Goal

Move this repository's tooling pin from v2.0 to v2.1 and prove, via its
self-referential CI, that v2.1 tooling validates cleanly against the repo. This
is the first 2.0 → v2.1 conversion in the fleet; it doubles as the lowest-risk
test bed and the source of the per-repo procedure the rest of the fleet will
repeat.

## Background: how the pin drives the tooling version

`vergil.toml` `[dependencies].vergil` is the single source of truth for which
`vergil-tooling` tag is installed. It is resolved by `vrg_install_tag()`
(overridable via `VRG_DOCKER_INSTALL_TAG`) and consumed in two places:

- **Local** — `vrg-container-run` / `vrg-validate` →
  `container_cache.ensure_cached_image()` computes a SHA-256 over the
  cache-sensitive files (for a `shell` repo, just `vergil.toml`, salted by repo
  name) and looks for an image tagged `…--<branch>--<hash>`. On a miss it builds
  one with `uv tool install vergil-tooling@<pin>` and commits it; on a stale
  hash it deletes the old one first. The base images deliberately do **not**
  ship vergil-tooling.
- **CI** — `actions/shared/setup/vergil` reads the same pin and
  `uv tool install`s it in-job.

Because `vergil.toml` is part of the cache hash, changing the pin invalidates
the local cache and forces a rebuild with the new tag — so local validation is a
faithful pre-merge test, using the same install path as CI.

## Changes (the entire functional diff for this repo)

1. `vergil.toml` — `[dependencies] vergil = "v2.0"` → `"v2.1"`.
2. `CLAUDE.md:134` — host-install reference `vergil-tooling@v1.4` → `@v2.1`.
   Documentation only; aligns the stale host-CLI hint with the pin.

The pin value is the floating `v2.1` tag (consistent with the prior floating
`v2.0`), tracking the latest 2.1.x patch.

## Why this repo needs no actions/workflow review

vergil-actions CI consumes its own actions through **local paths**
(`uses: ./actions/...`), not a pinned remote ref. There is therefore no
`vergil-project/vergil-actions/...@v2.x` reference to bump here, and the action
code exercised by CI is the PR's own code. This exemption is specific to
vergil-actions — see "Generalization to the fleet" for what other repos must do
in addition.

## Verification

- **Local:** `vrg-container-run -- vrg-validate`. The pin change busts the cache
  hash, rebuilding the per-branch image with `uv tool install
  vergil-tooling@v2.1` and running the full validator suite against it. A
  missing or non-floating `v2.1` tag fails here, loudly — the implicit
  pre-flight check.
- **CI:** open a PR; the self-referential workflows run every job under v2.1
  tooling. Green CI is the acceptance gate.

## Risk surface (what to watch in CI)

2.0 → 2.1 is a minor/feature bump, not a major break. The behavioral deltas most
likely to trip something:

- stricter `gh api` gating,
- identity-aware allowlists / agent denials,
- the `vrg-finalize-pr` consolidation.

If any CI job fails, that failure **is** a finding: record it in
vergil-tooling#1371 before fixing.

## Rollback

Revert the two-line change; the cache mechanism rebuilds the v2.0 image on the
next validate. This PR cuts no release, so blast radius is limited to the branch.

## Generalization to the fleet (feeds vergil-tooling#1371)

This canary establishes the per-repo procedure. Other repos differ from
vergil-actions in one structural way and share the rest:

- **Lockstep principle.** Upgrading "vergil" means upgrading the whole tooling
  collection — `vergil-tooling` *and* `vergil-actions` — to the same
  major.minor. Mixing major.minors across the collection can work if you are
  lucky, but it is unsupported; the desired state is everything on the same
  major.minor.
- **Third change for consuming repos.** In addition to the `vergil.toml` pin and
  stale-doc fixes, other repos must bump their consumed action refs
  (`uses: vergil-project/vergil-actions/...@v2.0` → `@v2.1`), because
  vergil-actions itself now tracks v2.1. vergil-actions is exempt only because
  it self-references via local paths.
- **Stale-doc hunting generalizes.** Each repo may carry its own stale
  tooling-version references (host-install lines, READMEs); the migration is a
  chance to find and normalize them.

## Scope boundaries

- **In scope:** the two-line change above, local + CI verification, feeding
  lessons into vergil-tooling#1371.
- **Out of scope:** other repos' bumps; repo-wide doc sweeps beyond the known
  stale reference; cutting a release.
