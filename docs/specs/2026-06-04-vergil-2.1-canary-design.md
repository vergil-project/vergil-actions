# vergil-actions v2.0 → v2.1 canary — design

- **Issue:** vergil-project/vergil-actions#679
- **Playbook (fleet docs):** vergil-project/vergil-tooling#1371
- **Date:** 2026-06-04
- **Status:** approved (design); revised after `paad:pushback` review

## Goal

Move this repository's tooling pin from v2.0 to v2.1 and prove, via its
self-referential CI, that v2.1 tooling validates cleanly against the repo. This
is the first 2.0 → v2.1 conversion in the fleet; it doubles as the lowest-risk
test bed and the source of the per-repo procedure the rest of the fleet will
repeat.

## Background: how the pin drives the tooling version

`vergil.toml` `[dependencies].vergil` is the single source of truth for which
`vergil-tooling` tag is installed. It is resolved by `vrg_install_tag()`
(overridable via `VRG_DOCKER_INSTALL_TAG`) and consumed in two places:

- **Local** — `vrg-container-run` / `vrg-validate` →
  `container_cache.ensure_cached_image()` computes a SHA-256 over the
  cache-sensitive files (for a `shell` repo, just `vergil.toml`, salted by repo
  name) and looks for an image tagged `…--<branch>--<hash>`. On a miss it builds
  one with `uv tool install vergil-tooling@<pin>` and commits it; on a stale
  hash it deletes the old one first. The base images deliberately do **not**
  ship vergil-tooling.
- **CI** — `actions/shared/setup/vergil` reads the same pin and
  `uv tool install`s it in-job.

Because `vergil.toml` is part of the cache hash, changing the pin invalidates
the local cache and forces a rebuild with the new tag — so local validation is a
faithful pre-merge test, using the same install path as CI.

## Changes (three-change set for this repo)

The pushback review showed this is more than the two-line change it first
appeared to be — though one suspected change (a `VERSION` bump) turned out to be
unnecessary; see "No VERSION bump needed" below. The set:

1. **`vergil.toml`** — `[dependencies] vergil = "v2.0"` → `"v2.1"`. The pin that
   drives the installed tooling version (Axis 1, below).
2. **`actions/ci/security/standards-compliance/action.yml:13`** —
   `…/setup/vergil@v2.0` → `@develop`. This is a GitHub Actions *git ref*
   (Axis 2, below), not driven by `vergil.toml`. It is an absolute remote ref
   because `standards-compliance` is consumed remotely by other repos, where a
   `./actions/...` relative path would not resolve. It should track `@develop`
   so the self-referential PR exercises the current line, and
   `freeze-internal-refs` pins it to `@v2.1` at release. The `@v2.0` value was a
   stale leftover from the original bootstrap of self-referential CI.
3. **Docs (full sweep)** — bring every current consumer-facing version
   reference onto the v2.1 line: `CLAUDE.md:134` host-install
   `vergil-tooling@v1.4` → `@v2.1`; all `…@v2.0` references in
   `.github/workflows/README.md` (11) and across the published docs site
   `docs/site/docs/**` (55) → `@v2.1`. These are the release refs downstream
   repos copy, so they track the release tag, not `@develop`. Historical
   records are excluded — `docs/specs/**` design docs and `docs/plans/**` are
   point-in-time and left as-is.

The pin value (change 1) is the floating `v2.1` tag, consistent with the prior
floating `v2.0`, tracking the latest 2.1.x patch. **The `v2.1` tag is confirmed
present** (created 2026-06-04), so there is no missing-tag risk.

### No VERSION bump needed (version-divergence already satisfied)

The version-divergence gate (`ci-version-bump.yml` →
`actions/ci/version-bump/version-divergence`) fails only when the PR-branch
`VERSION` equals `origin/main`'s. In the normal post-release state, `develop` is
already one patch ahead of `main`, so a feature branch off `develop` already
diverges and the gate passes without any bump. **Verified: `origin/main` =
`2.1.0`, `develop` = `2.1.1`** → already diverged. A `VERSION` bump would only be
needed if `develop` and `main` were equal (e.g. first release, or a release
where `develop` was not post-bumped). This PR therefore leaves `VERSION`
untouched, and the release tooling continues to own version management.

### Two version axes (why some refs propagate and some do not)

- **Axis 1 — installed tooling version.** Driven by `vergil.toml`
  `[dependencies].vergil` (change 1). Propagates automatically to every install
  path (local cache build + CI `setup/vergil`).
- **Axis 2 — GitHub Actions `uses:` git refs.** Resolved by GitHub at
  workflow-parse time; *not* read from `vergil.toml`. Changes 2 and 3 live on
  this axis and must be updated explicitly. On `develop` the canonical form for
  an unavoidable absolute ref is `@develop` (frozen to the release tag by
  `freeze-internal-refs`); consumer-facing examples use the release tag.

## Action/workflow refs in this repo (mostly self-referential)

vergil-actions CI consumes its own actions through **local paths**
(`uses: ./actions/...`), so the action code exercised by CI is the PR's own
code — there is no consumed-from-elsewhere `@v2.x` ref to bump for the bulk of
it. The one exception is `standards-compliance/action.yml:13` (change 2): an
unavoidable absolute remote ref, because that action is consumed remotely by
other repos where a relative path cannot resolve. It is corrected to `@develop`
here. There is no other in-repo `@v2.x` action ref in executed code; the
remaining `@v2.0` strings are consumer examples in `.github/workflows/README.md`
and the published docs site `docs/site/docs/**` (change 3, docs).

## Verification — two gates

Acceptance is split, because the PR's CI does not exercise the release path.

- **Local (pre-PR):** `vrg-container-run -- vrg-validate`. The pin change busts
  the cache hash, rebuilding the per-branch image with `uv tool install
  vergil-tooling@v2.1` and running the full validator suite against it.
- **CI gate (the PR):** open a PR; the self-referential CI workflows (`ci.yml`:
  docs, quality, security, version-bump) run every job under v2.1 tooling. Green
  CI proves v2.1 is fine **for CI**.
- **CD gate (first post-merge release):** the CI gate does **not** run the
  release/publish path (`cd-release.yml`, `tag-and-release`, finalize/merge) —
  and the riskiest 2.1 deltas live there (see risk surface). The real test of
  the release path under v2.1 is the **first release cut after this merge**.
  Watch it explicitly as a follow-up; do not declare the upgrade fully proven
  until it is green.

## Risk surface (where the 2.1 deltas live)

2.0 → 2.1 is a minor/feature bump, not a major break. The behavioral deltas most
likely to trip something are concentrated in the **CD/release path**, not CI:

- stricter `gh api` gating,
- identity-aware allowlists / agent denials,
- the `vrg-finalize-pr` consolidation.

Because these sit in the release path, the CI gate will likely pass cleanly
while the genuine exposure is deferred to the CD gate. If any job in either gate
fails, that failure **is** a finding: record it in vergil-tooling#1371 before
fixing.

## Rollback

Revert the change set; the cache mechanism rebuilds the v2.0 image on the next
validate. `VERSION` is untouched, so this PR does not itself force a release —
but once merged to `develop` the change is included in the next normal release;
revert before that release cuts if the canary is judged unsafe. Blast radius
before merge is limited to the branch.

## Generalization to the fleet (feeds vergil-tooling#1371)

This canary establishes the per-repo procedure. Other repos differ from
vergil-actions in one structural way and share the rest:

- **Lockstep principle.** Upgrading "vergil" means upgrading the whole tooling
  collection — `vergil-tooling` *and* `vergil-actions` — to the same
  major.minor. Mixing major.minors across the collection can work if you are
  lucky, but it is unsupported; the desired state is everything on the same
  major.minor.
- **Consumed action refs (Axis 2) for other repos.** In addition to the
  `vergil.toml` pin and stale-doc fixes, other repos must bump their consumed
  vergil-actions refs (`uses: vergil-project/vergil-actions/...@v2.0` → `@v2.1`),
  because vergil-actions itself now tracks v2.1. These point at the **release
  tag** `@v2.1`. vergil-actions is the special case: it self-references via
  local paths and `@develop`, not release tags.
- **VERSION vs the divergence gate — usually a no-op.** A releasing repo's PR
  must have `VERSION` differ from `origin/main`. In the normal post-release
  state `develop` is already one patch ahead of `main`, so feature branches
  inherit a diverged version and need **no** bump (the canary confirmed this:
  develop `2.1.1` vs main `2.1.0`). A bump is only required when `develop` ==
  `main` (first release, or a release where develop was not post-bumped). Check
  before assuming a bump is needed.
- **Two-gate verification generalizes.** A green PR proves CI under v2.1; the
  release/publish path is only proven by the first post-merge release. Watch it.
- **Stale-doc hunting generalizes.** Each repo may carry its own stale
  tooling-version references (host-install lines, READMEs); the migration is a
  chance to find and normalize them.

## Scope boundaries

- **In scope:** the three-change set above (pin, the `standards-compliance` ref,
  docs); local + CI verification (CI gate); watching the first post-merge
  release (CD gate) as a follow-up; feeding lessons into vergil-tooling#1371.
- **Out of scope:** other repos' bumps; repo-wide doc sweeps beyond the version
  references named above; deliberately cutting an off-cycle release just to test
  CD (the next normal release serves as the CD gate).
